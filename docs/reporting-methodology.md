# روش‌شناسی گزارش و تعریف وضعیت‌های AMDB

## مرجع واحد
`project-status.json` تنها منبع داده داشبورد است. `current_status` تنها مرجع snapshot فعلی، شمارش فنی، وضعیت release، QA، پنل‌ها، امنیت و دیتابیس است. سایر بخش‌ها جزئیات محصول، قابلیت‌ها، تصمیمات معماری یا تاریخچه‌اند و نباید با آمار فعلی جمع شوند.

## هویت و محدوده مخزن
- فارسی: بانک اطلاعاتی فیلم افغانستان
- انگلیسی: Afghanistan Movie Database
- مخفف: AMDB
- دامنه: https://amdb.af
- مخزن کد محصول: https://github.com/armanaria111/amdb-laravel2
- مخزن گزارش: https://github.com/armanaria111/amdb-report

این مخزن فقط گزارش و داشبورد را نگهداری می‌کند؛ هیچ فایل برنامه، Migration یا داده دیتابیس AMDB از اینجا تغییر داده نمی‌شود.

## چهار وضعیت مستقل
1. **پیاده‌سازی در سورس:** کد در شاخه main موجود و PR مربوطه ادغام شده است.
2. **تست موجود:** تست مربوطه در مخزن وجود دارد؛ این به معنی اجرای آن نیست.
3. **تست اجراشده:** خروجی واقعی PHPUnit یا ابزار تست با تاریخ/commit ثبت شده است.
4. **تأیید runtime/production:** رفتار در محیط اجرا یا محیط عملیاتی به‌صورت قابل تکرار بررسی شده است.

مقادیر وضعیت قابلیت:
- `implemented_unverified`: پیاده‌سازی در سورس main تأیید شده؛ runtime/QA تأیید نشده است.
- `partial`: بخشی از نیازمندی پیاده‌سازی شده یا کار محصولی/QA مشخصی باقی است.
- `needs_review`: نیازمند بازبینی یا تصمیم؛ کامل فرض نمی‌شود.
- `planned`: هنوز پیاده‌سازی نشده است.
- `blocked`: وابسته به تصمیم، داده یا زیرساخت بیرونی است.

وجود قابلیت در main هرگز به معنی سلامت runtime نیست. قابلیت‌های خبری، جشنواره، API، رسانه، اعلان‌ها و پیشنهاد اصلاح اطلاعات در snapshot فعلی در گروه پیاده‌سازی‌شده در سورس قرار دارند.

## آمار فنی
Snapshot در `current_status.source_inventory` از Git tree شاخه `main` و بازبینی lock/config و `routes/web.php` تهیه می‌شود. هر عدد باید با تاریخ و commit مشخص نمایش داده شود.
- Git tree entries: ورودی‌های درخت Git؛ نه تعداد فایل‌های کد خالص.
- Migration files: تعداد فایل‌های migration در سورس؛ نه تعداد اجراشده.
- Eloquent model files: تعداد فایل‌های مدل؛ نه تعداد جدول‌ها.
- Blade files: تعداد فایل‌های Blade.
- Translation PHP files: تعداد فایل‌های زبان.
- Test PHP files: تعداد فایل‌های تست؛ نه تعداد تست‌های موفق.
- Named route calls: تعداد فراخوانی‌های `->name(`؛ نه الزاماً endpointهای یکتا.
- Route declarations: شمارش ایستای رخدادهای تعریف Route؛ نه فهرست endpointهای یکتا.

## دیتابیس
- تعداد جدول‌های واقعی فقط پس از دسترسی read-only به دیتابیس و استخراج schema قابل ثبت است.
- تعداد Migrationهای اجراشده فقط با خروجی تازه `php artisan migrate:status` ثبت می‌شود.
- در نبود این شواهد، مقدار باید `null` و برچسب «تأییدنشده» باشد.
- هیچ Migration صرفاً به‌دلیل وجود در GitHub اجراشده فرض نمی‌شود.
- قبل از هر Migration در محیط دارای داده، backup و بررسی محیط مقصد الزامی است.
- از `migrate:fresh`، `db:wipe` و هر بازسازی مخرب استفاده نشود.

## پنل‌ها
وضعیت پنل مدیریت، کاربر عادی و هنرمند از feature map و شواهد سورس خلاصه می‌شود. این وضعیت، کامل‌بودن UX یا تست مسیرهای انتها‌به‌انتها را اثبات نمی‌کند. مالکیت، مجوزها، جریان درخواست‌ها، اعلان‌ها و پرداخت باید جداگانه QA شوند.

## امنیت
ممیزی‌های امنیتی همراه commit و تاریخ اصلی نگهداری می‌شوند. یافته قدیمی تا بازبینی روی commit فعلی «یافته تاریخی/نیازمند بازبینی» است؛ remediation ادغام‌شده نیز تا اجرای تست و بررسی runtime «رفع‌شده عملیاتی» محسوب نمی‌شود. ریسک‌های داده‌ای مانند فایل‌های legacy باید مستقل از کد جدید گزارش شوند.

## QA و انتشار
فیلدهای کیفیت در `current_status.quality` مستقل نگهداری می‌شوند: تست‌های موجود، اجرای تست و نتیجه، build، مرورگر، smoke test و اجرای Migration. اگر اجرا نشده‌اند صریحاً false/نامشخص ثبت می‌شوند. نتیجه موفق فقط با خروجی و commit قابل ردیابی ثبت شود.

## تاریخچه و درصد پیشرفت
ممیزی‌های قدیمی در `historical_archive`، تاریخچه توسعه و اسناد آرشیوی حفظ می‌شوند؛ اعداد آن‌ها نباید در نمای فعلی تکرار شوند. درصد کلی پروژه نمایش داده نمی‌شود؛ تا زمانی که وزن‌دهی، دامنه و معیار قابل سنجش و قابل بازتولید تعریف نشده است، این درصد گمراه‌کننده خواهد بود.
