# روش‌شناسی گزارش و تعریف آمار AMDB

## هدف

این مخزن فقط گزارش، تاریخچه و داشبورد پروژه **بانک اطلاعاتی فیلم افغانستان (Afghanistan Movie Database — AMDB)** است. کد برنامه در مخزن جداگانه `amdb-laravel2` نگهداری می‌شود.

## تنها مرجع وضعیت فعلی

بخش `current_status` در `project-status.json` تنها مرجع آمار فعلی داشبورد است. بخش‌های دیگر فایل شامل جزئیات دامنه، قابلیت‌ها، تصمیمات معماری و تاریخچه هستند و نباید به‌عنوان snapshot آماری جداگانه تفسیر شوند.

## تعریف وضعیت قابلیت‌ها

- `implemented_unverified`: کد در شاخه main ادغام شده، اما تست/runtime یا انتشار عملیاتی آن تأیید نشده است.
- `partial`: بخشی از نیازمندی پیاده‌سازی شده و کار محصولی/QA باقی مانده است.
- `needs_review`: به بازبینی یا تصمیم نیاز دارد؛ پیاده‌سازی کامل فرض نمی‌شود.
- `planned`: هنوز به‌عنوان قابلیت پیاده‌سازی‌شده ثبت نشده است.
- `blocked`: وابسته به تصمیم، داده یا زیرساخت بیرونی است.

وجود کد در main هرگز به معنی سالم‌بودن قطعی آن در runtime نیست.

## تعریف آمار فنی

Snapshot فعلی در `current_status.source_inventory` با استفاده از GitHub recursive tree شاخه `main` مخزن اصلی و بازبینی فایل‌های `composer.lock`، `package.json` و `routes/web.php` تهیه شده است.

- Git tree entries: تعداد ورودی‌های درخت Git در snapshot؛ نه تعداد فایل‌های کد خالص.
- Migration files: تعداد فایل‌های PHP در `database/migrations`؛ این عدد تعداد Migrationهای اجراشده نیست.
- Eloquent model files: تعداد فایل‌های PHP زیر `app/Models`؛ نه تعداد جدول‌ها.
- Blade files: تعداد فایل‌های `.blade.php` زیر `resources/views`.
- Translation PHP files: تعداد فایل‌های PHP زیر `lang/en`، `lang/fa-AF` و `lang/ps`.
- Test PHP files: تعداد فایل‌های PHP زیر `tests`؛ این عدد به معنی اجرای تست نیست.
- Named route calls: تعداد فراخوانی‌های `->name(` در `routes/web.php`؛ لزوماً تعداد endpointهای یکتا نیست.
- Route declarations: تعداد رخدادهای `Route::` در فایل بررسی‌شده؛ گروه‌ها و تعریف‌های تودرتو باید با دقت تفسیر شوند.

## دیتابیس و Migration

گزارش ساختار سورس را از وضعیت دیتابیس زنده جدا می‌کند:
- تعداد جدول‌های واقعی دیتابیس تا زمان اتصال read-only و بررسی schema برابر «نامشخص» است.
- تعداد Migrationهای اجراشده تا زمان دریافت خروجی تازه `php artisan migrate:status` برابر «تأییدنشده» است.
- هیچ Migration را صرفاً بر اساس گزارش GitHub اجراشده فرض نکنید.
- قبل از هر Migration در محیط دارای داده، backup و بررسی محیط مقصد الزامی است.
- هرگز از `migrate:fresh`، `db:wipe` یا بازسازی مخرب برای همگام‌سازی گزارش استفاده نشود.

## QA و انتشار

چهار وضعیت مستقل نگهداری می‌شوند:
1. وجود کد/PR ادغام‌شده در main
2. وجود تست در مخزن
3. اجرای واقعی تست/build
4. تأیید runtime یا محیط عملیاتی

اگر مرحله‌ای اجرا نشده باشد، باید صریحاً «اجرا نشده» نمایش داده شود؛ نباید از روی وجود فایل تست یا migration نتیجه‌گیری شود.

## ممیزی‌های تاریخی

ممیزی‌های قبلی همراه تاریخ و commit اصلی خود نگهداری می‌شوند. یافته‌های قدیمی امنیتی یا معماری تا زمان بازبینی مجدد روی commit فعلی، یافته تاریخی هستند و نباید به‌عنوان ریسک قطعی نسخه امروز نمایش داده شوند.
